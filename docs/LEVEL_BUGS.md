# Bugs in the original level data

As of 2026-10-30. A collection of bugs in the shipped levels and scripts (`.zax`, `.RDS`), not in Zax.exe: the exe does what the data says, but the data does not do what the designers meant. Bugs of the exe itself are in `zax-decomp/docs/ORIGINAL_BUGS.md`. They are collected here and fixed in a later phase (with the other fixes: opt-in, original behaviour by default, `zax-decomp/docs/ORIGINAL_BUGS.md` "Fix").

Each entry: what goes wrong, when, the objects involved (level, part number in the Tree List, name), the code that makes it happen, the evidence level, a fix idea, and whether the editor's level check could warn about it.

**The fix pack**: `levels/make_level_fixes.py "<game folder>" -o LevelFixes.RED` of the private pack tools (zax-packs; in this repository until 2026-11-10) makes it from the player's own `DATA.dat` (L.1 and L.7; whole levels, so never shipped). Beside the game it is active in the original `Zax.exe` and in the port for as long as it lies there; the port's launcher lists it on its Packs page, where it can be unticked. With it in the folder the game is no longer the original: a recorded play of `01 Main` differs. L.2 to L.6 are left out on purpose: no visible effect is known, and making those scripts work would change the game in ways nobody has looked at.

**L.1 Valeth's secret ore cave (mission 7) stays shut after a normal mission 3** — `ACT 1/M1M2/01 Main`, `ACT 1/M3/03 SI Cave`
- What: in mission 7 a healthy Valeth leads Zax through `03 SI Cave` back to `01 Main` and is meant to open `door to secret area` (part 659, via `prox trigger2 for secret gate` 710) for a cave full of ore. But Zax arrives at `Spawn Point Cave` (806) behind the closed cave exit `gate` (805), the ship's computer says an item from the cave is missing (`Mission01n2` line `Missing piece`), and the gate never opens. Zax can only go back into the cave (`go back`, 827).
- Why: the spawn action of `Spawn Point Cave` is a `CSeriesAction` with `Require Success To Advance=1` and `When Done=Repeat Last Action`, one step per arrival. Step 0 checks for `Junk B` and `Junk A` (the two metal objects of mission 3), and its success action is `CActivateAction` `shut gate, ore path`. Step 1 opens `gate` when the mission 7 Valeth (`follow me`, 782) is active. But `CActivateAction` succeeds only when a target **was inactive** (`Activate_AtTarget` `0x4c29f0`, `zax-decomp/reimpl/src/action_slots2.cpp`; several targets OR-ed, `Action_EachTarget` `0x41aed0`, `zax-decomp/reimpl/src/action_helpers.cpp`), and `CConditionalAction` returns the success action's result (`0x41bba0`, `zax-decomp/reimpl/src/action_helpers.cpp`). In `03 SI Cave` picking up `tech bit` (335) already activates `shut gate`, and the lever (362, `Cave Door Switch 1`) activates `ore path, shut gate`, both through `COtherMapAction`. Those queued actions run on the map switch before the spawn action (`App_SwitchMap` `0x59b400`, `zax-decomp/reimpl/src/c4_app2.cpp`: `COtherMapList::RunFor` `0x41f6c0`, then `MoveAllToSpawns`). So in the normal order (object, lever, exit), step 0 fails silently although Zax carries both objects, the series stays at step 0, and in mission 7 step 0 runs again without them (the ship's medical station used them up, `Inside Ship` `check for junk poly`).
- When: every playthrough that pulls the lever before leaving the cave the first time in mission 3, i.e. the intended order. Not when Valeth was hurt in mission 7 (`07 Village Main` `valeth2.1` takes over, says `no key` and skips the detour).
- Workaround in the game: in mission 3 leave the cave with both objects before pulling the lever (`ore path` is still inactive, step 0 succeeds), walk back in through `go back`, pull the lever, leave again. Reported by a player on Reddit (r/AskGames, thread `nz2nns`), matching the code.
- Impact: an optional reward (the ore cave and Valeth's dialogue) is lost; the story goes on (back through `03 SI Cave` to `07 Village Main` `back from the secret`). Side effect: Valeth's last step never runs, so `close up` never deletes `Inside Ship` `door locked relay` [assumption: what that changes on the ship is not followed].
- Evidence: [confirmed: level data + code, the functions above]; not run in the VM.
- In the pack (`make_level_fixes.py`, 2026-11-09): a `CSucceedAction` added to step 0's `CMultipleActionsAction`. The patched level loads and starts in the port and in the original exe [verified: VM (x86)]; the second arrival at the cave, which is where the fix shows, was **not** reached in a test (three attempts to force it failed in the test setup): the effect stays [confirmed: code].
- Fix: candidate (opt-in). In the data: step 0's success action must report success even when the targets are already active, e.g. a `CSucceedAction` added to its `CMultipleActionsAction` (whose result is the OR of all its actions, `MultipleActions_Execute` `0x4b87a0`, `zax-decomp/reimpl/src/action_slots.cpp`), or drop `Require Success To Advance`. Editor: possible warning for a `CSeriesAction` with `Require Success To Advance` whose step's result is a `CActivateAction` on objects other scripts activate too (open).

## Minor findings (no visible effect found)

Found by a scan of all 112 levels on 2026-10-30 (series steps that can fail after doing their work, missions and objectives; the scan's rules are the exe's result rules from the reimplementation: `CMultipleActionsAction` OR of all, `CConditionalAction` 0 after its Fail branch, the named actions only when they changed something). Each one is a script error in the data, but the scripts around it show no effect in the game [assumption: not run in the VM]. Kept here so a later data fix can correct them together.

**L.2 Actions on names no object has** — the action does nothing and returns failure; in each case the trigger runs once, the series' later steps repeat the same work, or nothing triggers it
- `ACT 2/M14/14 Stones Main` part 170 (Gate Switch 1): `CToggleDoorAction` `outer temple kluge door` (no such object; the series' other actions toggle `outside temple door2` in both steps, so the behaviour is the same).
- `ACT 2/M8/08 Pits Cave1` part 389 (proximity trigger for Butu, `Trigger Only Once=1`) and 799 (`control panel1`, Cage Control Panel): `CToggleDoorAction` `door1`/`door2` and `CSetCurSequenceAction` `cp1`/`cp2`; the level has no object of these names (the slaves are released by their `CSendAIDoneMessage`).
- `ACT 3/M21/21 Double Trouble` part 87 (`off-map multi-door opener`, a relay): `COpenDoorAction` `Door1`, `Door2`, but the doors are named `Door 1`, `Door 2`; nothing triggers this relay.
- Name typos next to an existing similar name (found 2026-10-30 by comparing every unresolved door, relay, activate and AI-done name with the level's names); the scripts around them do the work another way: `ACT 1/M5/05 Azah-Pan Main` part 621 closes `Mission 05 gate` in `01 Main` (the gate is `Mission 5 Gate`); `ACT 2/M14/14 Stones EndLevel` part 217 sends AI done to `Azah-Pan` (the boss is `Azah Pan`, which part 315 releases as well); `ACT 3/M18/18 Slave Main` part 1142 (`key door`, Before Open) triggers the relay `you jacked it up` (only `you jacked it up again` exists, so that reaction never happens); `ACT 3/M20/20 Hydro Generator` part 878 deactivates `trap out` and `light fence korbo` in `20 OutsideWaste` (the fields are `trap out1`-`3`, switched off there by parts 248 and 143). Plus about 80 relays nothing triggers (left-overs such as `Cave1 relay` in `08 Pits Cave1`, replaced by the count objective's increments) and gaps in numbered ranges (`fire on fence #1-20#` with some numbers missing); not listed one by one.

**L.3 `CSelectMission` of a mission that does not exist** — `ACT 2/M10/10 Mining Hub` part 70 and `ACT 2/M10/10 Mining Map2` part 152 (`Main Spawn`, step 2 of the spawn series, every later arrival) select `M10`; the missions are `M10b` (defined in step 1 of the Mining Hub spawn), `villa` (step 1 of the Mining Map2 spawn) and `Mission 10`. `SelectMission_Execute` `0x513210` (`zax-decomp/reimpl/src/missions.cpp`) reports the unknown tag and keeps the current mission, so the mission log is not switched back on a return [assumption: intended the mission each spawn defines in its step 1].

**L.4 `CUpdateMissionObjective` of an objective no mission has** — `ACT 1/M6/06 Elec Fence Main` part 102 (`warp`) completes `Node on`; mission `M06` has `Power Node` (completed elsewhere) and `power disturbance`. `find_objective` (`zax-decomp/reimpl/src/missions.cpp`) only reports it. Two more are guarded by `CIsMissionObjectiveDefined` and therefore deliberate: `Inside Ship` part 11 (`1st to ship`) and `ACT 2/M12/12 WaterTempleCourt` part 569 (`find jungle switch`).

**L.5 Missions defined twice with different content** — a second `CDefineMission` with a tag already in use is refused (`DefineMission_Execute` `0x512d20`). Most pairs are a debug start point (`cheater`, `Cheat Start`) next to the normal one and only differ when a game starts there. Open: `ACT 2/M9/09 Assimilate Main` defines `Mission 09` in part 743 (objective `Din`) and in part 774 (`warp`, objective `Key 1`); whichever runs second is refused, `Key 1` is also added by part 780 (`poli`). Which runs first, and whether the log loses an objective, is not followed.

**L.7 The "Expired Zone" sign shows only in Salvage King** — `Levels/Expired Error` part 6 (the `CUnderConstructionLayerPart` "You have been transported to another dimension, one in which a previous map was expired. You are in the Expired Zone"). The level cache loads this level instead of an expired one (`CSwappedLayerFilenameMappingTable::LoadPath` `0x5892b0`, `zax-decomp/reimpl/src/models.cpp`), but the sign has `Used In=MultiPlayer/Salvage King`, so in a quest game the zone is black around Zax and nothing explains it [verified: VM, `/Original`, the own levels of batch gaps-world's `wexpire`, recording run `20261101-171949-bc3a`, `10_expired.png`; zax-decomp/docs/DECOMPILATION.md 13, "Batch gaps-world"]. No retail level expires a map it can return to, so a player only meets it through a level bug of that kind [assumption: not checked for every `CExpireMapAction`]. Fix: in the pack (`make_level_fixes.py`, 2026-11-09): `Used In` lists every game mode, as the levels' other parts do [verified 2026-11-09: VM (x86): the sign shows in a quest game with the pack, in the port and in the original exe, and not without it]. Level check: no.


## Open leads (possible effect, not confirmed)

**L.6 The moon lock in Assimilate Temple1 also takes a Sun key** — `ACT 2/M9/09 Assimilate Temple1` part 625 (model `Lock, Sun`, opens `Moon door`, the way to `09 Assimilate Temple2`): after using the Moon key it runs `CConditionalAction` "has `Key, Sun`" -> `CUseInventoryItemAction` `Key, Sun`. Next to it the Sun lock (part 649) needs a Sun key for `Sun door` (the way to `09 Assimilate Cave1`), and `sun moon prox` (635) says Zax needs "a Sun and Moon key". If the player opens the moon door first while carrying a Sun key, the key is gone [assumption: whether enough Sun keys remain depends on the order of the mission 9 maps (keys: Temple1 parts 127, 507; Temple2 421; Cave2 119 Partha; Main 924; locks: Temple1 266, 649; Temple2 354; Cave2 1033; Main 786) and was not followed; a VM run from a save at that door would settle it]. A copied sun lock script is the likely origin.

Checked without a finding (2026-10-30): every item a script checks or uses has a source (placed pickup, `CCreateDefaultEntityAction`, give action, or the multiplayer player model for the flags); every level transition's target level and start point exist; "Trigger Only Once" triggers are consumed only when their action succeeds (`TriggerAI_Fire` `0x422cd0`, `zax-decomp/reimpl/src/ai_triggers.cpp`; relays in any case, `0x420290`), and the once-triggers that can succeed with a failed condition inside skip only optional work (objective updates guarded by `CIsMissionObjectiveDefined`, dialogue, map expiry).
