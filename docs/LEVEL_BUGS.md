# Bugs in the original level data

As of 2026-10-30. A collection of bugs in the shipped levels and scripts (`.zax`, `.RDS`), not in Zax.exe: the exe does what the data says, but the data does not do what the designers meant. Bugs of the exe itself are in `zax-decomp/docs/ORIGINAL_BUGS.md`. They are collected here and fixed in a later phase (with the other fixes: opt-in, original behaviour by default, `zax-decomp/docs/ORIGINAL_BUGS.md` "Fix").

Each entry: what goes wrong, when, the objects involved (level, part number in the Tree List, name), the code that makes it happen, the evidence level, a fix idea, and whether the editor's level check could warn about it.

**The fix pack**: `levels/make_level_fixes.py "<game folder>" -o DataFixes.RED` (named LevelFixes.RED until 2026-11-14; it also carries one data fix outside the levels, the 16-bit mute image, `docs/FORMATS.md` `Cache/Interface/`) of the private pack tools (zax-packs; in this repository until 2026-11-10) makes it from the player's own `DATA.dat` (L.1 and L.7; whole levels, so never shipped). Beside the game it is active in the original `Zax.exe` and in the port for as long as it lies there; the port's launcher lists it on its Packs page, where it can be unticked. With it in the folder the game is no longer the original: a recorded play of `01 Main` differs. L.2 to L.6 are left out on purpose: no visible effect is known, and making those scripts work would change the game in ways nobody has looked at.

**L.1 Valeth's secret ore cave (mission 7) stays shut after a normal mission 3** — `ACT 1/M1M2/01 Main`, `ACT 1/M3/03 SI Cave`
- What: in mission 7 a healthy Valeth leads Zax through `03 SI Cave` back to `01 Main` and is meant to open `door to secret area` (part 659, via `prox trigger2 for secret gate` 710) for a cave full of ore. But Zax arrives at `Spawn Point Cave` (806) behind the closed cave exit `gate` (805), the ship's computer says an item from the cave is missing (`Mission01n2` line `Missing piece`), and the gate never opens. Zax can only go back into the cave (`go back`, 827).
- Why: the spawn action of `Spawn Point Cave` is a `CSeriesAction` with `Require Success To Advance=1` and `When Done=Repeat Last Action`, one step per arrival. Step 0 checks for `Junk B` and `Junk A` (the two metal objects of mission 3), and its success action is `CActivateAction` `shut gate, ore path`. Step 1 opens `gate` when the mission 7 Valeth (`follow me`, 782) is active. But `CActivateAction` succeeds only when a target **was inactive** (`Activate_AtTarget` `0x4c29f0`, `zax-decomp/reimpl/src/action_slots2.cpp`; several targets OR-ed, `Action_EachTarget` `0x41aed0`, `zax-decomp/reimpl/src/action_helpers.cpp`), and `CConditionalAction` returns the success action's result (`0x41bba0`, `zax-decomp/reimpl/src/action_helpers.cpp`). In `03 SI Cave` picking up `tech bit` (335) already activates `shut gate`, and the lever (362, `Cave Door Switch 1`) activates `ore path, shut gate`, both through `COtherMapAction`. Those queued actions run on the map switch before the spawn action (`App_SwitchMap` `0x59b400`, `zax-decomp/reimpl/src/c4_app2.cpp`: `COtherMapList::RunFor` `0x41f6c0`, then `MoveAllToSpawns`). So in the normal order (object, lever, exit), step 0 fails silently although Zax carries both objects, the series stays at step 0, and in mission 7 step 0 runs again without them (the ship's medical station used them up, `Inside Ship` `check for junk poly`).
- When: every playthrough that pulls the lever before leaving the cave the first time in mission 3, i.e. the intended order. Not when Valeth was hurt in mission 7 (`07 Village Main` `valeth2.1` takes over, says `no key` and skips the detour).
- Workaround in the game: in mission 3 leave the cave with both objects before pulling the lever (`ore path` is still inactive, step 0 succeeds), walk back in through `go back`, pull the lever, leave again. Reported by a player on Reddit (r/AskGames, thread `nz2nns`), matching the code.
- Impact: an optional reward (the ore cave and Valeth's dialogue) is lost; the story goes on (back through `03 SI Cave` to `07 Village Main` `back from the secret`). Side effect: Valeth's last step never runs, so `close up` never deletes `Inside Ship` `door locked relay` [assumption: what that changes on the ship is not followed].
- Evidence: [confirmed: level data + code, the functions above]; not run in the VM.
- In the pack (`make_level_fixes.py`, 2026-11-09): a `CSucceedAction` added to step 0's `CMultipleActionsAction`. The patched level loads and starts in the port and in the original exe [verified: VM (x86)]; the second arrival at the cave, which is where the fix shows, was **not** reached in a test (three attempts to force it failed in the test setup): the effect stays [confirmed: code].
- Fix: candidate (opt-in). In the data: step 0's success action must report success even when the targets are already active, e.g. a `CSucceedAction` added to its `CMultipleActionsAction` (whose result is the OR of all its actions, `MultipleActions_Execute` `0x4b87a0`, `zax-decomp/reimpl/src/action_slots.cpp`), or drop `Require Success To Advance`. Editor: possible warning for a `CSeriesAction` with `Require Success To Advance` whose step's result is a `CActivateAction` on objects other scripts activate too (open).


**L.8 The deployed Companion Drone Light has no description** — `Levels/Global/Inventory Item Text.rds`, label `'Deployed Companion Drone Light' Description ` (with a trailing space)
- What: the item's Info text is in the script, but its label ends with a space. `Item_Description` `0x4d67c0` builds the key `'<name>' Description` from the trimmed name and `CPropertyList::Lookup` `0x41e5a0` compares exactly, so the label never matches and the deployed drone shows the default "This item has no description" (the same mechanism as the tab-ended labels of `GERMAN.RED`, `FORMATS.md` 2).
- When: the inventory Info of a deployed Companion Drone Light; in the standard `DATA.dat` and in the language packs checked (German, Spanish, Chinese, Russian), each with the same trailing space.
- Evidence: [confirmed: code, as for the tab-ended labels; the label read from the data of each edition]; the Info window itself was not opened in a test.
- In the language and fix packs of the private pack tools (2026-11-09/10): the space removed, the text unchanged (EnglishFix, GermanFix, 0SpanishFix, 0ChineseFix, RUSSIAN). Not in `DataFixes.RED`, which holds only levels.
- Fix: candidate (data). Editor: yes (a label with leading or trailing white space never matches).

**L.9 The key door in Slave Main never raises the alarm** — `ACT 3/M18/18 Slave Main` part 1142 (`key door`, its `Before Open`), part 1086 (the `Door Switch` that opens it), part 1108 (`distraction`, an explosive barrel), relay part 841 (`you jacked it up again`)
- What: the key door is meant to set off the alarm when Zax opens it while the guards have not been lured away: its `Before Open` is `CIfAction` "`distraction` alive" -> if the relay `you jacked it up again` is not active: activate it, `CTriggerRelayAction`, deactivate it again (the same three-step pattern as in the scripts of the guards `peris patroler`, `talon guard`, `key guard 2` (its `Attack Start Action`), `Key guard hidden`, `this guy` and of the barrel itself). But the trigger step names `you jacked it up` (the relay of `15 Northern Main`); only `you jacked it up again` exists in this level, so `CTriggerRelayAction` finds no target and nothing happens (`CTriggerRelayAction::AtTarget` `0x420290` runs only a found target's `CRelayAI`, `zax-decomp/reimpl/src/ai_triggers.cpp`; the activate/deactivate around it leave the relay as it was).
- The relay it should fire is the level's alarm (`COnlyOnceAction`): Sentinon AIs and collision for the 16 `alarm turrets1`, the five `Red spawn pads trap1`-`5` turned on with generators of Talons and Periscopes (`bad guys1`-`5`), and `hide again` and `First dialog by lava wall` switched off.
- When: whenever the player opens the key door with its switch without first blowing up the barrel `distraction` (whose `Destroyed Action` sends `key guard 2` away to `distraction point1`); the intended stealth step can be skipped without any consequence. Being seen by one of the guards still raises the same alarm through their own scripts.
- Evidence: [verified: VM, original exe (`/Original`), own copies of the level under `Levelbugs/` with a start point next to the switch (the start point touches it on arrival); run `20261114-085106-cb0f` unchanged: no alarm in 21 s, health 100; run `20261114-085106-47c2` with only the relay name corrected: the spawn pads warp in Talons and Periscopes within 6 s, Zax is dead after about 10 s ("Mission Failed: Life functions have ceased"); control run `20261114-085327-f7b6`, corrected name but the switch made inactive: no alarm, so it is the switch -> key door -> `Before Open` that fires it].
- Impact: the level is easier than designed; nothing is lost. No soft lock either way.
- Fix: candidate (opt-in), in the data: `Relay Name=you jacked it up again` in part 1142's `CTriggerRelayAction`. For `DataFixes.RED`: not recommended as a default fix: it does not restore lost content but adds a punishment players of the original never met (in the test the alarm killed Zax within seconds at the switch); if wanted, as a separate opt-in ("designed difficulty"). Editor: possible warning for a `CTriggerRelayAction` whose name matches no relay of the level (the scan of L.2 below lists them).

## Minor findings (no or only a small visible effect)

Kept here so a later data fix can correct them together.
