# File formats of "Zax: The Alien Hunter"

Reconstructed from the game files and `Zax.exe`. There is no official documentation.

**Evidence levels** – every statement is marked:

- **[verified]** checked on all affected files of the complete Data.zip (mostly via `tools/selftest.py`)
- **[confirmed]** shown on examples or confirmed by strings/code in `Zax.exe`
- **[assumption]** plausible and consistent with the data, but not proven

All binary formats are little-endian.

---

## 1. Data storage

- The game loads everything from the folder `Data/` or from `Data.dat` (an uncompressed zip file with the same content). [confirmed]
- The game's `Data.dat` (718,215,852 bytes, 4,982 entries, names without `Data/`, e.g. `Levels/ACT 1/M1M2/01 Main.zax`) is a normal zip file except for the signature at the end of the central directory: `RE\5\6` instead of `PK\5\6`. Common zip programs therefore find no directory. Zax.exe accepts both signatures (`0x5c22e5`/`0x5c22ec`). [verified] `zaxtools.datasource.DataSource` still reads it directly: a read wrapper returns the 4 bytes of the signature as `PK\5\6`, the file stays unchanged (self-test with Data.dat and with the folder `Data/`, 0 failures each, 2026-10-20). [verified]
- The game runs completely from the unpacked folder `DATA/` if `Data.dat` is removed (Windows VM, 2026-10-18). [verified]
- If both `Data.dat` and `DATA/` exist, the file on disk wins: a changed `.zax` in `DATA/` is loaded although `Data.dat` contains the original (Windows VM, 2026-10-20). [verified] Cause [confirmed]: in read mode (flag 4) the open function `0x4a2440` first only reads entries with marker +0x2f from a zip file (search with flag 0x8000). The directory list `0x5c2970` only sets this marker for entries whose name is not already in the list from disk (FindNextFileA, `0x4a4c15`); initially it is 0. After that `0x4a2440` opens the file on disk and only then every zip entry. Absolute paths (`\`, `/`, drive) set flag 0x20 and bypass the zip files completely (`0x4a1840`). Writing only goes to disk.
- **Localised editions** come as another archive next to `DATA.dat`, in the German edition `GERMAN.RED` (83,240,145 bytes, 786 entries). It is an ordinary zip with `PK\5\6`, the entries are not compressed and have paths as in `Data` [verified]. At start (`0x4cd780`) `0x4a0c40` mounts the archives with the base name `Data` in this order: first the exe itself (`GetModuleFileNameA`, `0x4d2370`), else `Data.ZIP`, else `Data.DAT`, then all `*.RED` from the game folder, sorted by name (search `0x4a0a30`, `qsort`) [confirmed: Zax.exe]. An entry of the `.RED` replaces the one of the same name in `DATA.dat` [verified 2026-10-20, VM: with `GERMAN.RED` in the game folder the opening dialogue of `01 Main` appeared in German and the display "Erz" instead of "Ore"]. Files on disk below `Data/` also win against the `.RED` (see above). A changed English `.RDS` from the editor in `Data/` would therefore cover the translation in the German edition [confirmed: code `File_Open` `0x4a2440` (the file on disk before the archive entries of every root, `.RED` included), `ZZipList::Open` `0x5c1c70`, zax-decomp/reimpl/src/disk_stream.cpp, zip_archive.cpp; VM]. The editor can add a language pack (`DataSource(root, language_pack)`, menu File → Choose language pack …). In that case the pack also wins against the folder `Data`, because that counts as an unpacked `Data.dat`.
  - Content of `GERMAN.RED` [verified]: except for 7 entries it only replaces files of the same name.
    - 24 dialogue scripts `.RDS`.
    - 724 voice recordings `.ogg`.
    - `Movies/Intro.bik`.
    - 30 enemy radio messages (`Sounds/ENEMIES/…`) as silent `.wav` of 370 bytes: they are not translated but muted.
    - New are `Local.txt` (section 2.3) and 6 `.ogg`. 2 of them have the name of a `.wav` in `Data`, 4 have no counterpart there.
    - `.ogg` next to a `.wav` of the same name [confirmed 2026-10-28: code `CSoundList::Load` `0x57e2f0`, `CSoundList::Find` `0x57e690`]: the sound list keeps both as separate entries (name with extension). A lookup takes the exact name first and only tries the other extension (`.wav` ↔ `.ogg`) when it is missing. A reference to `x.wav` therefore plays the `.wav` while it exists; the `.ogg` of the same name is only a fallback.
- **The other editions** [verified 2026-10-29: SHA-1 per archive and per entry, decoded texts; `gamedata/Zax - <language>/`]:
  - **One `DATA.dat` for five editions**: English, German, Spanish, Polish (`Data.dat`) and Chinese ship the same file (718,215,852 bytes, SHA-1 `7ffde7c4…`, `RE\5\6`); the language is only in the pack. Only the Russian edition has its own `DATA.dat` (below).
  - **Which archive wins** [confirmed 2026-10-29: code `0x5c1c70`]: a file is opened "from the last root to the first", and every `.RED` is a root of its own, mounted in name order (`_stricmp`) after `DATA.dat`. So of two packs with the same entry the one later in name order wins. The names follow that: the main packs start with `0` (`0Spanish.RED`, `0Chinese.RED`), the patches with `1` (the French patch `1French.RED`, the Chinese edition's Windows 2000/XP fix that its `Win2kxpfix.bat` copies to `1ChineseW2k_XP.RED`). For the French patch to win, the French main pack must sort before it, e.g. `0French.RED` [assumption: the French edition is not here]. `GERMAN.RED` and `Polish.red` (2001, without patches) have no prefix.

  - **The Russian edition** has no pack and translates inside a rebuilt `DATA.dat` (717,342,546 bytes, 5,052 entries, 53 of them folder entries, SHA-1 `559cf888…`): 887 entries changed, 52 files new, 35 gone. Translated: the 24 `.RDS` (CP1251, speakers too: "Зак", "Зелон"), 755 voices plus 13 multiplayer announcements, 26 fonts with the Cyrillic letters at CP1251 codes, `ZaxCredits.txt`, `Movies/intro.bik`, `Movies/JoWooD.bik`, `Interface/Splash Screen 3.bmp` (the Russian logo). The same play without the pack writes none (`20261101-221337-79a6`: `Key, Moon.txt` absent after loading `18 Slave Main`). **Why** [confirmed: code `Object_WriteFile` `0x4167e0`, `File_Exists` `0x4a1650`, `ZZipList::Exists` `0x5c1d00`, `ZZipDir::Exists` `0x5c2830`, `File_DiskTest` `0x4a3d70`; verified 2026-11-09 below]: the write-back runs only if `File_Exists` says yes, and that function does not simply test for a file. `ZZipList::Exists` asks only the last mounted root. Without a pack that is `DATA.dat`, which holds the file: the answer is the byte "archive on disk", 0 for a root mounted without check_disk, so `File_Exists` says no and nothing is written. With a pack the last root is the `.RED`, which does not hold the definition: the archive path gives up and the disk test decides, which is true for a writable file and also for a missing file whose **folder already exists**. So a definition is rewritten only if a pack is mounted, the last pack does not hold it, its folder exists on disk, and the normalised text differs from the file read (`Object_WriteFile` compares first). Measured 2026-11-09 [verified: VM (x86), Windows 11; the 1308 exe alone, no launcher or DLL, in fresh folders, a new game into `01 Main`, the level reached in every run]: `GERMAN.RED` and no `Data` folder: nothing written; only `Data/Inventory/Item Definitions/` present: `Zelon Gun` written, the two in `Enemy Weapons/` and the one in `Shields/` not; those two subfolders present as well: all 4; the same folders without the pack: none. A normal installation has no such folder, so it writes nothing (an archived, long-played German installation with `GERMAN.RED` has no `Data` folder). The folder appears when something else puts files there (a mod, the editor, a test job); the VMs' game folders had such folders, since they wrote there [assumption: left by earlier jobs, the file lists show no folders]. The files that land there are the same definitions with `Item Priority=0` added and hold no translated text; later starts read them from disk (the folder `Data` wins) [confirmed: code `File_Open`].
  - **The menus' accelerators follow `Local.txt`** [verified 2026-11-01: VM, screenshots `20261101-213801-da9b`]: the translated texts carry their own `&`, so the German game menu takes B for "Spiel &beenden" (E&nd Game: N) and E for "&Einstellungen" (&Configure: C); "&Spiel speichern" (S) and "Spiel &laden" (L) keep theirs; the main menu's "S&piel starten" is P, "&Impressum anzeigen" I, "B&eenden" E; in the configuration menu "&Steuerelemente einstellen" and "&Sound einstellen" share S (video: "&Grafik einstellen", G). "Enable Weapon Auto-Switching" in the controls and the launcher's "Load Map (F9)" stay English (no pair in `Local.txt`).

## 2. Text format (`.zax`, `.txt`, `.zgt`, `.can`, `.sty`, `.dificulty`, `.quips`, `.foo`)

Implementation: `zaxtools/textformat.py`. Lossless reading/writing of all 425 files. [verified]

- Encoding ASCII/Latin-1, line ending CRLF, indentation with tabs. [verified]
- One line `key=value`. If a line is followed by a line `{`, the value is the class name of a sub-object that extends up to the matching `}`. [verified]
- The root is a class name without `=` (e.g. `CLayerSaveData`). [verified]
- Arrays: `Name=Array` with the first entry `Item Count=N` (sometimes `Array Count=N`), then the elements. Element keys repeat. [verified]
- Raw lines without `=` occur: embedded images as hex, e.g. `Fog Of War=CFrame(1,1,8)` with lines like `01`. [verified]
- Values can have trailing spaces (e.g. `First Map Spawn Point=Game Start `) – do not trim. [verified]
- The field names are the engine's property names. The exe registers them with name, type and offset; many have a tooltip text in the exe (a good source for their meaning). [confirmed]

### 2.1 Level (`.zax`, root `CLayerSaveData`)

Implementation: `zaxtools/level.py`.

Header fields (selection):

| Field | Meaning |
|---|---|
| `Width`, `Height` | map size in world pixels (e.g. 4097×4097, 5000×5000) [verified] |
| `Partial File Name` | own path below `Levels/` without extension; also the mini map path [verified] |
| `Map Description` | display name |
| `Default Game Type`, `Allowable Games` | QuestMode or multiplayer modes (`Resources/Game Types/*.zgt`) |
| `Suggested Num Players`, `Max Players` | multiplayer |
| `Music Mix` | three music files (full, medium, ambient) below `Music/` |
| `Environment Type`, `Rolloff`, `Environment Size` | the exe's group "Listener Settings": reverb presets by name, but **no effect in the retail game** (the setters store values nothing reads, `zax-decomp/docs/ORIGINAL_BUGS.md` 1.17) [confirmed: code] |
| `Team Info` | array of `CTeamInfo` (index = team number): `Spawn Point Name` (where the game places a figure of the team without a start point name, e.g. "Select Map"), `Re-Spawn Point Name` (instead of it when the figure's player was placed before; multiplayer levels "random"), `Model Type` (model list resource; "!Unknown Model" in all 112) [confirmed: `World::MoveToTeamSpawn` `0x4f4950`, zax-decomp/reimpl/src/world_class.cpp]; 179 entries in 111 levels, `01 TargDens` has none [verified] |
| `View Position` | start camera |
| `Path Data` (`CWayPointMap`) | `MinDistBetweenWayPoints`, `MaxDistToConnect` – also stored in the header of the `.way` [verified] |
| `Active Paths` | cached paths (runtime state) |
| `Fog Of War` | fog map of the **mini map** as `CFrame` (hex, 16 bit: two bytes per pixel, little endian), see below [confirmed] |
| `MiniMap X/Y Scale/Offset`, `* Mini-Map Clipping` | world → mini map: `px = x·XScale + XOffset`, `py = y·YScale + YOffset` [confirmed] |
| `Tree List` (`CSortList2D`) | all objects, each `Level Part=<class>` |
| `Plasma Ground` (`CPlasmaTileMap`) | ground, see 2.2 |

Many fields are runtime state that is saved along (`Has Begin Been Called`, `Shake Time`, `Is Marked For Deletion`, `Current Target` …). An editor should leave them unchanged.

Common fields: `Name`, `Visible`, `Collideable`, `Has Hit Points`, `Stationary`, `Active`, `Activity` (array with AI/triggers), `Team Number`, `Used In` (game modes), `Model`, `Position X/Y` (world pixels, also decimals), `Rendering Height` (pixels above the ground, section 6), `Cur Sequence`. A `CEntityAnimated` with `Active=0` is absent in the game: not drawn, no collision, cannot be shot, until a script switches it on [verified 2026-10-20, 11 models]. Polygons: `Polygon=x1, y1, x2, y2, …` as a closed polyline (last point = first). [verified for 01 Main]

Animated and movable objects (15,916 over all levels) additionally have `Start FacingAngle`, `Movement Angle`, `Aiming Angle` (radians; e.g. 0.523599 = 30°) and `Current Frame`. Static `CEntityBase` objects have no angle fields. [verified] Angle → rotation: section 6 (formula from the exe).

**Surfaces (`CRenderablePolygon`)**, derived from `CFreeRangePoly` (`Collideable=1` also makes the surface an obstacle; 75 surfaces, mainly lava). Own fields according to the exe: `On Ground`, `Render Type`, `YSort`, `Cur Frame`, `Animated Texture`, `Static Texture`, `Warp Effect`. [verified on all 112 levels]
- `Render Type`: the exe knows `Warped`, `Animated Texture`, `Textured`, `Trans Red`, `Trans Green`, `Trans Blue`, `Shadow`, `Black`; the levels only use: `Black` 2,024 (77 levels, `On Ground=0`), `Textured` 187 (33 levels, almost always `On Ground=1`; water, lava, snow, temple floor) and `Animated Texture` 131 (30 levels, `On Ground=1`; `Water Green Dark`/`Water Blue Dark`, section 5.1). [verified]
- Unused texture fields are almost always `Static Texture=01 Ivy`, `Animated Texture=!None`, `Warp Effect=!None` – the game's defaults [confirmed: code `CRenderablePolygon::RegisterFields` `0x55d4a0` gives the three fields no default name, so `CResourceFieldSlots::SetDefault` `0x54e2c0` sets index 0, the first entry of each list (`01 Ivy`, `!None` in name order), zax-decomp/reimpl/src/render_poly.cpp, resource_fields.cpp; VM].
- `Black` draws black; with `On Ground=0` the surface lies above the objects (Zax disappears below it) [verified 2026-10-19]. In the originals black surfaces are almost always covers (`On Ground=0`; names like "hidden", "fake", "before drill", category `Top Hide`); 22 lie on the ground (`On Ground=1`): then Zax stays visible on them [verified 2026-10-19].
- **Order (`YSort`, `On Ground`)** [confirmed: code `0x55dc30`/`0x55dd90`; verified 2026-10-20 in the game, test level `Test/YSort`]: a surface is sorted in like a layer of an object, key `(bottom edge of the polygon + YSort) · 8`, the left edge on ties (comparison `0x49c9a0`). `On Ground=1` puts it into the ground queue (with the layers that have `Render On Ground`: shadows, ground marks, earth), `On Ground=0` into the object queue; the game draws the whole ground queue first, then the other one (`0x4e7c00`). Consequences: water on the ground always lies below all objects, `YSort` only orders it relative to shadows and ground marks (−800 for almost all water surfaces: below the shadows); a black cover only hides what stands higher than its bottom edge + `YSort`. In the test level: a cover with `YSort` 0 hides the crate inside it, not the one below; with +200 both, with −200 neither; crates in water with `YSort` 0, −800 and +2000 are all visible; a crate lies above the earth (`jungle dirt 2`, `Render On Ground`) at the same place although its key is larger; the crates' shadow is only visible in the water with −800. Exception: Zax's shadow stays visible while walking on any water, also with `YSort` 0 (`Test/Wasser`) [verified 2026-10-20]. A standing Zax also keeps his shadow [verified 2026-10-20]. Cause [confirmed: code `0x4e7c00`, `0x4e8810`, `0x4e8080`, `0x4886a0`]: every frame `0x4e8810` marks the rectangles of all non-resting entries of both queues as changed (`0x480fc0`). `0x4e8080` then draws in every changed tile only the non-resting entries from the ground queue and all from the object queue, each in queue order and clipped to the tile. Resting ground parts are not redrawn there; they remain from the background image [confirmed 2026-10-29: code `CPlasmaTileMap_DrawLayer` `0x540b80`, `Layer_DrawTileOnce` `0x4e8ce0`, zax-decomp/reimpl/src/tile_map_draw.cpp, layer_draw.cpp; VM; see the tile cache below]. The second branch of `0x4e8080` depends on `0x6c1cf7`; that byte lies in the uninitialised data area and is written nowhere, so it is always 0 and the branch is dead (like `g_NoCutting`). An entry counts as resting (byte `+0x24` = 0) if the object carries the runtime flag `0x200000` (`+0x1c`), the layer has no `Auto-Animate`, the fade value is ≥ 1 and the flag `0x400000` is missing; surfaces only by the flag `0x200000` (`0x55e007`). The fade value is `CEntityAnimated +0xb4` (vtable `+0x170` = `0x48f510`), set to 1.0 by the constructor (`0x48e994`) and to 0…1 by `CEntityBehaviorFade` when fading in and out (`0x498600`). The flag `0x200000` is the field `Debug/Stationary` (`CLayerPart`), saved as `Stationary=1` for every object of the original levels [verified: 82,137 top-level objects, never 0]; the behaviours clear it when they begin or play and set it again when they end (e.g. `0x497241`/`0x4965c2`), objects that are not `CEntityAnimated` get it after every drawing (`0x488f18`). Consequence: walking characters and their shadows lie above all resting ground parts regardless of `YSort`; the standing crate (`CEntityAnimated`), however, follows `YSort`. A standing Zax does not rest because idling clears the flag on every update [confirmed: code]: the player's control (`0x543b60`) runs its embedded `CEntityBehaviorIdle` every frame while he stands, and its update (`0x4990e0`) restarts the idle sequence of a walking entity every time (`Idle_Start` `0x498fa0`, which clears `Stationary`); `CEntityBehaviorPlaySequenceLooped` (`0x499d50`) clears it on every update too. The background with the resting ground parts is the tile cache of the Plasma Ground: `CPlasmaTileMap_DrawLayer` `0x540b80` builds a 64 × 64 tile once from the ground and the resting ground entries (`Layer_DrawTileOnce` `0x4e8ce0`; the second layer also the resting object entries, `Layer_DrawTile` `0x4e8b60`, both through `0x4e8bd0`, which takes the entries with byte `+0x24` = 0); `World_DrawDirtyTiles` `0x4e8080` then draws the non-resting ground entries and all object entries above it in the changed tiles. So the order the game shows is: ground and resting ground entries by key, then the non-resting ground entries by key, then the object queue. Verified 2026-10-29 in the game (`Test/Anim`, `/Original`, jobs `20261029-062126-72e1`, `20261029-062604-b900`): in a textured water surface with `YSort` 0 the crate's shadow is hidden, the `Auto-Animate` shadow of `Torch 1` (`Idle Animation Shadow`) and the floor light of a `Light Beam 2` playing with `CPlaySequenceLoopedAI` lie above the water (torch area 100.00 % identical to the renderer with the rule, 99.29 % without). Implementation: `zaxtools/anim.py` (`layer_resting`), `render.render_level` (ground queue in two groups), editor `scene.LowLayerItem` (`Z_LOW_MOVING`). Values: `YSort` exists in all 2,326 surfaces; ≠ 0 for 1,296 (`Black` above the objects e.g. 137–566, water/texture on the ground almost always −800). Without the field: `YSort` 0, `On Ground` 1 (constructor `0x55d880`). Implementation: `render.surface_key`, editor `scene.SurfaceItem`.
- **`Collideable` must be set:** if the field is missing, Zax can walk into the surface but not out again – it acts like a movement area (`CFreeRangePoly`). ### 2.2 Ground (`Plasma Ground`)

- `Num Textures` + `Texture 0..n-1`: names below `Cache/Textures/` (1 to 30 per level). [verified]
- `Elevations Row i`: one grid row as hex, 1 byte per point. Grid = `ceil(Width/64)` columns × `ceil(Height/64)` rows (usually equal to `Width/64 + 1`; different if the size is a multiple of 64), point (r, c) lies at world (c·64, r·64). [verified on all 112 levels]
- Texture selection: `value · NumTextures / 256` gives the texture index (band); interpolated between grid points, blended towards the end of the band (see `Blending`). [confirmed: comparison with the mini maps of 01 Main and 15 Northern Main; Zax.exe]
- Confirmed by painting in the editor [verified 2026-10-18, editor test level]: grid points set to `(index + 0.5) · 256 / count` give the chosen texture in the game (according to the exe half mixed with the next one at `Blending=1`, see below; since 2026-10-19 the editor paints at the band start); areas, islands and transitions across intermediate bands match the renderer in shape. In the game the transitions were somewhat softer and the image darker overall than in the renderer at that time – explained by band start/blending, the plasma fractal and the 16-bit rounding down (below).
- Changing the texture list (editor, `groundedit.remap`): every grid point keeps its texture and its relative position in the band (`new = (new index + fraction) · 256 / new count`). New textures go to the end; then the image stays the same (renderer: at most 7 of 255 deviation in 01 Main). Inserted in the middle, existing transitions run across the new bands (5 % of the area changed). Reordering changes the transitions for the same reason. Because the band width changes, every change rewrites all `Elevations` rows. [verified with the renderer; verified in the game 2026-10-18: a list of 8 textures from different sets (Dirt, Hydro Plant, Om Ship, Temple, Water, Black Metal), ground painted with it appears as in the editor]
- Ground textures must be 128×128: `Special/Under Construction` (32×32, the only smaller one) appears as torn stripes in the game – the game apparently always reads 128×128. The editor does not offer it. [verified]
- `Blending` (float, default 0.25 without the field): share of the band over which it blends towards the next texture. [confirmed: Zax.exe, `CPlasmaTileMap`, function at 0x541710] The game computes for each of the 256 values: `t = value · count / 256`, band `i = floor(t)`, position `f = t − i`; share of texture `i + 1` = `(f − (1 − Blending)) / Blending`, at most 1, and 0 as long as `f ≤ 1 − Blending`; the top band never mixes. At 16/24 bit it mixes linearly (share · 255), at 256 colours via 5 grid levels (boundaries 0.2 / 0.4 / 0.6 / 0.8). A grid cell whose four corners have the same pure texture is drawn as a whole tile. Values in the originals: 1 (39 levels), 0.35 (38), 0.85 (17), 0.5 (7), 0.95 (5), 0.25 (4), 0.8 and 0.75 (1 each). Confirmed in the game [verified 2026-10-20, test levels `Test/Blend100` and `Test/Blend035`: the same slope `13 Rock` → `14 Black` over 13 grid points, only `Blending` 1 or 0.35]: the mean brightness per image column in the screenshot deviates by 2.5 or 3.5 (of 255) from the renderer, compared crosswise by 12.4. At 0.35 the ground stays pure until about two thirds of the slope and then quickly turns black.
- Consequence: a texture is only pure at the **start** of its band (at `Blending=1` only exactly there). That is why the original editor paints at the smallest value of the band: 24 % of all grid points lie exactly there, 3.3 % in the middle of the band. [verified on all 112 levels] Since 2026-10-19 the editor paints the same way (`render.band_start`); before, it painted at the middle of the band, which at `Blending=1` mixes in half of the next texture according to the exe – this matches "darker/softer in the game" above, not re-checked in the game. Against the original mini maps the new formula is closer than the old fixed width at `Blending=1` in 24 of 29 levels, otherwise about the same (mini maps are too small for details).
- **Between the grid points** the game fills every 64×64 tile with a plasma fractal (midpoint displacement with random values), not bilinearly – hence the irregularly frayed transitions. Procedure, random generator (R250, 256 fixed seeds) and rounding: `zaxtools/plasma.py`. [confirmed: Zax.exe from 0x540d90; the reimplementation matches the original code executed in an emulator byte for byte] In the game screenshot of "Eigene/Level 1" the frayed edges are in the same places as in the reimplementation; the share of ivy falls from 1 to 0 between value 0 and 128 as computed. [verified 2026-10-19, screenshot]
- `Seeds Row i`: a grid of the same size, almost everywhere 0 (e.g. 8 entries in 01 Main). Selects the random generator of the plasma fractal at this grid point (edges: seed or seed + 0x55, area: seed − 0x56). [confirmed: Zax.exe] A different seed therefore only changes the pattern of the fraying.
- **Mixing at 16 bit** (0x541541): alpha = `int(w · 255)`, per channel in RGB565 `A + floor((B − A) · (alpha >> 3) / 32)` for red/blue, `(alpha >> 2) / 64` for green. The rounding down makes every mixed pixel half a colour step darker on average (R/B ≈ 4, G ≈ 2 of 255), unmixed ones (w = 0) stay unchanged. That is why dark blotches appear in the game wherever the plasma falls just below a band boundary (e.g. Dirt at 128 with ivy below: value 127 gives almost pure Dirt, but rounded down). In the game screenshot of level 1: a jump at value 128 of 8.1 in the game, 8.8 in the reimplementation (red); before (mixed linearly) 1.4. [verified 2026-10-19] At 256 colours the game uses 5 levels via blend tables instead (not reimplemented).
- Textures tile in world pixels (128×128). [confirmed]
- Implementation (`zaxtools/render.py`, since 2026-11-08): `render.Ground` computes the ground in pieces of 512 × 512 output pixels with small integer types – the textures packed as RGBX words, the band and the blend alpha as tables over the 256 ground values (built by `blend_weight` itself), the 16-bit mixing of `mix16` as one table per channel over (alpha level, A, B), the plasma tiles of a whole area in a few large batches (`PlasmaCache.ensure`, locked for use from several threads). `render_ground` gives the same pixels as the former whole-box computation [verified 2026-11-08: all 112 levels at step 1 and 2 byte for byte; self-test: boxes across piece borders on every level], in about a fifth of the time (01 Main at full resolution 13.5 s → 1.7 s) and without the large intermediates (peak 3.8 GB → the output image). `Ground.rgbx(box, step)` gives a box as RGBX bytes (the editor's tiles, `zaxeditor.scene.GroundTiles`).

### 2.4 Field values: names, flags, limits, missing fields

How the game reads and writes the value of a field depends on its kind (the constructor of its descriptor; `zax-decomp/docs/DECOMPILATION.md` section 6, "Field kinds" and "Field values as text"). The editor reads kind, limits, default and name lists from the user's Zax.exe at run time (`zaxtools/exeschema.py`, nothing of it in the repository).

- **Missing field = default** [confirmed: code `CSortList2D::ReadOwnLine` `0x579560` → `Object_ReadFromStream` `0x416af0`, slot 19 `0x417230`]: every `Level Part` is created by class name, every field gets its descriptor's default (slot 10), then the lines are read. A field that is missing in the text therefore has the default; the editor's "Feld hinzufügen" writes exactly that default as text, at the place of the field in the registration order (the writer's order). [verified in the game 2026-10-28, `/Original`, `01 Main` edited in the editor: `Category=` added to a `CWayPointsPolygon`, `Used In` of `Spaceship` without `QuestMode` (the hull is missing at the crash site, present in the unchanged level), `Display Type` of the first intro line `Center Fade No Pause` (the dialogue no longer stops at that line: after 28 s the window already shows the next line); the level loads, the diff has only these 3 lines]
- **Choices** (typed resource `0x54e560` whose list `+0x34` is a static enum table; slot 47 `0x54e600` returns it) [confirmed: code]: the value is the index of a name. Reading uses `Find` (case-insensitive, then the alternative names, e.g. `Unknown` for `Any` of the skeleton states) and `FindOrFail`: **an unknown or empty name ends the game** ("Fatal Not Found Error"). Written is the table's spelling. 56 fields (e.g. `Render Type`, `Movement Speed`, `Return to map`); all 48,660 such values of the 112 levels are names of their table in its spelling [verified: self-test].
- **Int with names / float with names** (`FieldDesc_AddEnum` `0x54da60`, `FieldDesc_AddEnumFloat` `0x54ed60`): written is the name of the value, else the number (`%u` resp. `%g`). Reading: `atoi`/`atof`; a value that has a name is kept, otherwise a name gives its value, otherwise the number is clamped. Quirk: a name text gives `atoi` = 0, so if the value 0 had a name, every name would read as 0 – no field of the retail exe has a named 0 together with other names [confirmed: schema]. Only 14 int and 6 float fields have names, one each (e.g. `None Selected` = -1, `Do not move while attacking` = 0).
- **Flags** (`0x414cf0`, 11 fields): names of the set bits joined by `,` without blanks, in list order [verified: all 172,081 values of the levels are written so]. The name lists are built from the game data at start: the files of `Categories` (`.txt`), `Damage Types` (`.txt`) resp. `Resources/Game Types` (`.zgt`, with subfolders), without folder, extension and a leading `-`, sorted with `_stricmp` [confirmed: `ZDefinitionList::Init`, `App_LoadGameData`]. Reading splits at `,` and looks each name up with `FindOrFail` (case-insensitive): **an unknown name, a blank after a comma or an empty name between commas ends the game**; an empty text and a final comma are harmless [confirmed: `0x414fa0`]. `$all` is only understood as the default (`Used In`, `Allowable Games`, `Damage Types` of `CPercentInvulnerableAI`), never in a text [confirmed: `0x414de0`].
- **Limits**: int and float fields clamp on reading unless both limits are equal ("no limits"); the enum int constructor turns equal limits into 0 … 0xffffffff (with units 0 … 0xfffffffe) [confirmed: `0x54d6e0`, `0x54d7f0`]. Of 65 int, 218 enum int, 334 float and 4 double fields, 8, 35, 141 and 0 have real limits. No value of the 112 levels lies outside its limits (the self-test counts the clamped ones: 0 of 1,107,859).
- **Number text** is the C runtime's `%g`: six significant digits, a three-digit exponent (`1e+014`, as in the levels) [verified: game data].

## 3. Dialogue scripts (`.RDS`)

[confirmed] Text, CRLF. Blocks of a label and speaker lines, separated by blank lines:

```
:Must have mineral
Zelon: You must have minerals to use the materials generator.
```

`CZaxDialogAction` in the `.zax` refers to it with `Script=ACT 1/M1M2/Mission01n2` (path below `Levels/`, without the extension `.RDS`) and `Line=<label>` (without the colon). All 646 dialogue actions of the 112 levels find their label exactly [verified]. A block ends at the blank line. One `.RDS` per mission, plus `Levels/Dialog Script.RDS`, `Multiplayer/Multiplayer.RDS`, `Global/Inventory Item Text.rds`. Localised editions replace all 24 via an archive of their own (`GERMAN.RED`, section 1); the labels stay English, only the text after `Speaker:` is translated [verified on `Mission01n2.RDS`]. Voice output is stored as `.ogg` below `VOs/`.

**How the game reads a script** [confirmed: code, `zax-decomp/reimpl/src/ai_triggers.cpp` `PropertyList_Load` 0x41e0f0, `zax-decomp/reimpl/src/memory_stream.cpp` 0x506140]. The scripts are the definition list "Dialog Scripts" (`0x62e7e0`, all `*.RDS` below `Levels`, `DefinitionList_LoadRds` 0x4f71a0); each one is a property list (`CPropertyList`, items `CDialogLine` with `Name` and `Text`):

- The file is read in memory (`CFileBuf` flag 0x204, `MemoryStream_ReadLine` 0x506140): a line runs up to the next CR, then one CR and one LF are skipped. A lone LF stays part of the line; the last line needs no line end (5 English and 6 German scripts end without one). A line of 3,999 bytes or more ends the reading.
- Item 0 is always `!None`. A line starting with `:` starts a new item; the name is the rest of the line, not trimmed. Lines starting with `//` are skipped (comments; none in the shipped scripts). Every other line is appended to the current item's text with `\n`; lines before the first `:` line are dropped. The text loses its trailing white space (`ZString::TrimRight` 0x4e0f20) when the next item starts and at the end. A blank line therefore ends nothing: it only adds a `\n` that the trim removes; a block may have several text lines (none of the shipped scripts has more than one).
- `Line=` is looked up in that list (`ResourceField_SetByName` 0x54e490: a missing name is "Fatal Not Found", the game exits). The comparison ignores case and takes the first item of that name in file order [confirmed: code `ZNamedList::Find` `0x591bd0`, slot 2 of the property list's vtable `0x5ed448` (`_stricmp` over the items in order, then the part after the last `/`, `0x591ac0`), zax-decomp/reimpl/src/named_list.cpp; VM] (all 646 actions of the originals name their item exactly).
- Speaker and text: `CZaxDialogAction::SplitLine` 0x5a4bd0 splits the text at the first `": "` if it starts within the first 20 characters (speaker before it, the rest left-trimmed); otherwise the speaker is empty and the whole text is the line. The dialogue window (`DialogueWindow_AddLine` 0x47cd20) trims the speaker, shows `???` for an empty one and writes `"%s: %s"`. In `Global/Inventory Item Text.rds` (177 items) and `Multiplayer/Multiplayer.RDS` (29) most texts have no speaker; they are not dialogue lines.
- Portrait: the sequence `Dialog Display/Dialog Window Frame/Portraits/<speaker> Portrait` of the list "Inventory Frames" (`0x6c0540`, folder `Inventory/Frames`, i.e. `Cache/Inventory/Frames`), else `…/!Unknown Portrait` (`DialogDisplay_Portrait` 0x47ccc0, strings `0x611040`/`0x611000`). ## 4. Way point graph (`.way`)

Implementation: `zaxtools/way.py`. All 112 files read/written byte for byte, consistency checked. [verified]

```
preamble   f32 27.0, f32 43.0, i32 0
header     i32 MinDistBetweenWayPoints, i32 MaxDistToConnect, i32 N
N nodes    f32 27.0, f32 43.0, i32 0, i32 0, i32 x, i32 y, i32 k, k × i32 edge index
           i32 M
M edges    f32 27.0, f32 64.0, i32 0, i32 1, i32 0,
           f32 length, f32 angle, i32 node A, i32 node B
```

- Every edge is in the lists of both end points. [verified]
- Length = Euclidean distance, at most `MaxDistToConnect`. Angle = direction A→B in radians, 0…2π. [verified]
- Self loops (A = B, length 0, angle π) occur regularly (in 01 Main 6,861 of 25,495), in all 112 files at 245,919 of 246,102 nodes, at most one per node; it appears twice in its edge list. The cause is a bug in the game [confirmed: code `0x538ae0`, numbers verified]: after inserting a node the game looks for all nodes within `MaxDistToConnect` (including the new node itself) and connects them to it. `cmp esi, [esp+0x40]` (`0x538d34`) is supposed to skip the new node, but it compares the position in the hit list instead of the node number. So almost every node gets an edge to itself; it is only missing where both happen to be equal (in the originals only at nodes 0 to 3). The loops are meaningless for path finding; `zaxtools/waymap.py` reproduces them (the files come out byte for byte).
- `f32 27.0` + type number is the general object signature of the binary serialisation (also in `.mdl`). [confirmed]
- The exe rebuilds a missing or unreadable `.way` itself when loading ("Calculating Way Point Map") [verified in the VM, OPEN_ISSUES 2]. Procedure [confirmed: code `0x4eca80` → `0x5383f0`]: for all way point polygons, in two passes by a field at `+0x74`, the game walks along the outline (`0x538230`), first unshifted, then offset outwards and inwards in fixed steps. Along every edge it places points (`0x5380d0`). A point becomes a node if it is free (`0x537d40`) and no node is closer than `MinDistBetweenWayPoints` (`0x539350`). Every new node is connected to all nodes within `MaxDistToConnect` (`0x538df0` → `0x538ae0` → `0x53a780`, duplicate edges are skipped). The step widths come from virtual methods of the world (`vtable +0xf8 … +0x108`): start offset 20, `MinDistBetweenWayPoints` 20, `MaxDistToConnect` 39.8, max offset 79.6, step 5, i.e. the outline shifted by 20, 25, … 35 [verified 2026-10-24 in the VM with `Test/Nachbau1`, logged by `zax-decomp/reimpl/src/checks_waypoint_map.cpp`; the reimplementation of `0x5383f0` builds the same `.way` byte for byte, zax-decomp/docs/DECOMPILATION.md section 7]. Then the file is saved (`0x4ec520`). For the unchanged `01 Main` the result is identical byte for byte to the shipped file [verified 2026-10-20, VM].
- **The editor builds the `.way` as the game does** (`zaxtools/waymap.py`, since 2026-10-29) [verified: all 112 shipped `.way` files byte for byte, `tools/selftest.py` section 2b; in the game 2026-10-29, `/Original`: the `.way` the game wrote for an edited copy of `09 Assimilate Cave1` (`Test/E2Cave`: a way point polygon moved, one with 30 points added, a wall copied; 2,204 way points, 7,651 segments) equals the editor's byte for byte, job `20261029-065716-68ce`; with the editor's `.way` in place the game loads it unchanged, job `20261029-065720-9dc2`]. Port of `0x5383f0` and what it calls from the reimplementation (`waypoint_map.cpp`, `polygon.cpp`, `math_tables.cpp`, `sort_list.cpp`); the x87 runs at 53 bits, so Python doubles plus float rounding where the original stores a float are exact. Details that decide the bytes [confirmed: code; each verified by the 112 files]:
  - Parameters: the world's slots 62–66 (`0x4f39f0`–`0x4f3a30`, the game's world vtable `0x602dc8` uses the base ones): offset 20, MinDist 20, MaxDistToConnect 20 · 1.99 = 39.8, max offset 2 · 39.8 = 79.6 (the earlier "79.8" above was a slip), step 20 · 0.25 = 5; offsets 20, 25, 30, 35 (below 39.8). The header therefore says 20/39 in every file, whatever the level's `Path Data` holds.
  - Order of the polygons: `CSortList2D::QueryClass` `0x57ab20` walks the 64-pixel cells column by column; a polygon comes at the first cell of its bounding rectangle, polygons of one cell in the order they were read. Only `CWayPointsPolygon` with the flag 0x200000 and none of 0x9d0000: `ResetFields` `0x5992c0` clears 0x9d0000 and the hidden flag fields are not read, so only `Tries To Collide=1` drops a polygon.
  - Polygon text (`0x5480e0` → `Polygon_Insert` `0x5466c0`): at most **25 points** (the rest of the line is dropped), a point equal to the previous one is skipped. Applies to every polygon field (collision, surfaces, paths); no shipped level has more than 25.
  - The free test `0x537d40`: with radius 0 (the unshifted outline) the query rectangle has no width, so those points are never blocked. Otherwise every part with all of 0x840000 and none of 0x190000 (active, collideable, no hit points, not "Tries To Collide", not deleted) whose kind-3 rectangle overlaps (x − r − 1, y − r − 1, x + r − 1, y + r − 1) blocks when its shape (slot 48) holds the circle (`0x5469c0`) at the point **minus the part's slot-43 position**. For entities that is the model's "Bounds Poly" (the only `POLY2D` block in the `.mdl16` header) at the position; for `CFreeRangePoly`/`CRenderablePolygon` slot 43 is the polygon's **first point** while the polygon is absolute, so the test runs at a point shifted by the first point (an original quirk: with the "correct" offset only 45 of 112 files come out right). Parts skipped: doors (`CDoorAI` in the part's or the model's Activity, slot 64), parts whose AIs refuse slot 65 (AND of AI slot 31 with no other part: `CTouchingPolygonTriggerAI` `0x4218c0`, `CPickupAI`/`CPickupDeployedItemAI` `0x53dea0`, `CTurnToBounceDirAI` `0x5706a0`, `CTurretAI` on an idle character `0x58e340`), `CUnderConstructionLayerPart` (slot 48 `0x4011e0` gives no shape). Without the models' Activity (it needs the exe schema) only 67 of 112 files come out right; the editor then marks the result approximate and does not write it.
  - Segment angle: `Table_Atan2` `0x509100` (the arc tangent table of thousandths, hence π for the self loops), into [0, 2π) with the float 2π.
  - Run time in Python: 74 s for all 112 levels, at most 4 s per level (2.5 s when the machine is idle).
- **Deleting the `.way` is not enough when the game has `Data.dat`** [verified 2026-10-29, `/Original`, job `20261029-065237-9c5d`]: for an edited `09 Assimilate Cave1` copied into `DATA\` without its `.way` the game wrote no `.way` – it found the shipped one in `Data.dat` (`File_CanOpen` `0x4a1570` sees the archive) and used that outdated network. A level under a new path (own levels) has no archived `.way` and is rebuilt. For edited originals the editor's own `.way` (File → Write the way point map) is the way to give the game the new network.

## 5. Images (`.frm`, `.frm16`) and frames

Implementation: `zaxtools/frm.py`. All 366 `.frm16` and 361 `.frm` decoded. [verified]

Header, 36 bytes:

| Offset | Type | Content |
|---|---|---|
| +0 | u8 | `0x31` |
| +1 | u8 | bits per pixel: 8 or 16 (the exe also knows `frm24`/`frm32`) |
| +2, +4 | i16 | hot spot x, y (signed; the anchor point in models) |
| +6, +8 | u16 | width, height |
| +10 | u16 | not written by the exe: `CFrame::WriteFrm` `0x4a9740` leaves these two bytes as the stack had them [confirmed: code]; 18 in all `.frm` and 254 of 366 `.frm16`, otherwise 310 … 4467 |
| +12 | u16 | flags: `0x20`/`0x40` raw, `0x2022`/`0x2044` RLE (bit `0x2000` = RLE) |
| +14 | u16 | high word of the frame's flags dword (written with +12 as one u32) [confirmed: code]; always 0 [verified] |
| +16 | u32 | size of the pixel block |
| +20 | u32 | size of the extra block – only 8-bit frames with alpha: the pixels with alpha 25–76 (see below) [confirmed 2026-10-28] |
| +24 | u32 | size of block +24 – only 8-bit frames with alpha: the pixels with alpha 76–127 (87 of the 361 `.frm`) |
| +28 | u32 | size of the alpha block (0 = none) |
| +32 | u32 | size of the edge block (0 = none) |

Then in this order, each followed by a row table (height × u32, offsets into the block): pixel block, extra block (+20), block +24, alpha block, edge block. Empty blocks are left out together with their table. In 8-bit frames of image sequences the alpha and edge blocks also occur individually (`sphere of zin/idle lights.seq`); they are then skipped. RLE blocks start with their own size (u32), so the first table row points to 4. [verified]

**The five blocks of 8-bit frames** [confirmed 2026-10-28: code, RLE encoder `RleEncode_Frame8` `0x4aef00`, 8-bit drawers `zax-decomp/reimpl/src/rle8.cpp`]: when a TGA with alpha is encoded for 8 bit, every pixel goes into one block by its alpha `a` (kept when `lo < a ≤ hi`): pixel block `a > 229`, edge block (+32) 178–229, alpha block (+28) 127–178, block +24 76–127, extra block (+20) 25–76; below 25 the pixel is dropped. The drawer draws them as five opacity steps: the pixel block opaque, edge, alpha and +24 block with the span pairs 1–3 of the mode (falling opacity), the extra block through the row function with the 20/80 blend (span tables T8/T9). A draw call with opacity below 1 shifts the blocks down the steps (`level = 5 − ⌊6 · opacity255 / 256⌋`, entry table `0x6757b8`); from level 5 nothing is drawn. 8-bit frames therefore have no alpha byte but a 5-step alpha.
- **The opacity of the steps** (8 bit on an 8-bit screen, "Copy" drawers `Rle8_DrawFull_Copy` `0x43e380` / `_DrawClipped_Copy` `0x43dbe0`, level 0) [confirmed: code, zax-decomp/reimpl/src/rle8.cpp, spans8.h; the tables: `FillGammaTable` `0x527420` makes row `r` of a factor `k` the nearest palette entry of `r · k + c · (1 − k)`, `InitBlendTables` `0x433000` builds `Alpha20_80` with 0.2 and `Alpha40_60` with 0.4, zax-decomp/reimpl/src/palette_rest4b.cpp, image_lo4.cpp]: pixel block copied (1), edge block T2/T3 = `Alpha20_80[dst · 256 + src]` (source 0.8), alpha block T4/T5 = `Alpha40_60[dst · 256 + src]` (0.6), block +24 T6/T7 = `Alpha40_60[src · 256 + dst]` (0.4), block +20 through the row `0x43ea00` with T8/T9 = `Alpha20_80[src · 256 + dst]` (0.2); each blend is the nearest palette colour. `frm.decode` draws an 8-bit RLE frame this way (`frm.OPACITY8` = 255, 204, 153, 102, 51, blended in RGB). Verified 2026-10-30 in the game (`/Original`, 8 bit, VM jobs `20261030-064034-7177` with the objects and `20261030-064041-3e10` without, test level `Test/Own8` on uniform ground, screenshots resampled to the game's 800 × 600): the shipped `Exploding Crate` (pixel and shadow bands) composited with the decoded 8-bit frames over the control screenshot deviates by 0.34 of 255 per channel (0.08 after taking the nearest palette colour), with the former decoding (the edge block with the alpha band's indices as opacity, bands +20/+24 left out) 3.48; an own soft-edged model whose alpha runs through all five bands 6.8 (3.5 after the palette step) against 19.7. (16-bit frames instead carry an alpha byte per run of the edge block, see the soft edges above.)

RLE per row, control byte `c`:

- `c < 0x40`: `c & 0x3f` pixels with the following value
- `0x40 ≤ c < 0x80`: `c & 0x3f` single values follow
- `c ≥ 0x80`: `c & 0x7f` transparent pixels, no data

A value is 1 byte (palette index) or 2 bytes (RGB565). [verified]

**Soft edges:** the pixel block contains the opaque pixels. The edge block contains the edge pixels (same RLE), the alpha block one byte of opacity (0–255) **per RLE entry** of the edge block, in reading order: one per single value (`0x40…0x7f`), one for a whole run (`c < 0x40`). Shadows consist only of edge pixels, mostly black; their inside is runs with an opacity around 153 (60 %). [verified: the number of bytes per row matches in all 49,142 model frames with soft edges; crate shadows compared with a game screenshot, 2026-10-19] Until 2026-10-19 the editor distributed the bytes per pixel, so the inside of the shadows was missing (only outlines visible).
- This holds for every 16-bit frame [verified 2026-10-29: all `.frm16` and `.seq16` of all editions and the demos and all `.mdl16` frames of the German edition, no exception]. In 8-bit frames the alpha block is never per entry: it is the image of the alpha band 127–178, an RLE image of its own with 1-byte values like the other bands (below). Until 2026-10-29 this section named "4 exceptions" (2 × `.frm`, 2 × `.seq16`); those were 8-bit files the per-row fallback of `frm._edge_alpha` happened to be noticed in; in fact the alpha block of every 8-bit frame with both blocks (87 `.frm`, frames of 81 `.seq`) is such a band image, and no 16-bit frame needs the fallback. Since 2026-10-30 `frm.decode` draws the five blocks of an 8-bit frame as the game's opacity steps (above); until then it drew the edge block with the alpha band's indices as opacity and left out the bands +20/+24.

**Encoder** (the game's TGA → frame compiler; `zaxtools/frm.py` `encode16`, `encode8`, `encode_raw`, `encode`/`values`) [confirmed: code `FrameFilterRle::Apply` `0x4afd40`, `RleEncode_Frame8` `0x4aef00`, `RleEncode_Frame16` `0x4af690`, the row encoders `0x4b0d80`–`0x4b18b0` with their probes `0x4b1aa0`–`0x4b1c90`, the depth conversion `FrameConvert_To8` `0x4ad1e0`/`_To16` `0x4ad920`/`FrameConvert_RleAlphaFrom32` `0x4aeba0`, `CFrame::WriteFrm` `0x4a9740`; reimpl `frame_load_rle.cpp`, `frame_load_convert.cpp`, `frame_rest4a.cpp`]:
- The RLE filter (kind 8/9 of the frame load filters) runs before the depth conversion (kind 11/12) on the loaded image. A 32-bit source (TGA with alpha) is split by alpha into bands (a pixel is kept when `lo < a ≤ hi`): for 16 bit the pixel block `a > 250` and one band 5 < `a` ≤ 250 encoded twice, once as the edge block and once as the alpha block; for 8 bit five bands (see above; an empty band other than the pixel block is left out). An 8- or 16-bit source without alpha is encoded as it is, with the value 0 transparent (`RleEncode_Bytes`/`_Words`).
- Each row: up to 127 transparent pixels as a skip code `0x80 | n`; the following non-transparent stretch as runs and literals. At each position the probe counts the equal pixels (at most 63); more than 8 make a run (`n` + one pixel). Otherwise a literal starts and grows pixel by pixel until it holds 63 pixels or the probe finds 8 equal pixels (at most 8 counted) at its next position; exactly 8 equal pixels therefore start a literal again instead of a run. "Equal" is per block: 16 bit pixel block the 5-6-5 pixel; 16 bit edge block the 5-6-5 pixel and `alpha >> 3`; 8 bit the nearest palette index; sources without alpha the value. A run stores its first pixel.
- The depth conversion then rewrites each block in place: the codes are copied and every stored pixel converted (8 bit: nearest palette index, 16 bit: `Pixel16_FromRGB` `0x433a10` with the tables of `InitBlendTables` `0x433000`, round(c · 31/255) and round(g · 63/255)); the 16-bit alpha block drops the codes and keeps one alpha byte per stored pixel. Each block starts with its size (u32), its row table holds byte offsets (the first 4).
- Header: `0x31`, depth, hot spot = negated origin, width, height, +10 not written, the flags as a u32 (`0x2022`, `0x2044`; raw `0x20`/`0x40`), the five sizes (a block's first dword; raw: width · height · bytes per pixel), then every non-empty block with its row table (raw: `y · width`).

### 5.3 Fonts (`Cache/Fonts`, `.seq`/`.seq16`)

Class `CFont` (parent class `CSequence`, fields according to Zax.exe: `First ASCII`, `Last ASCII`, `Fixed Width`). Built like an image sequence (section 5.1), but with signature `(27.0, 654.0)` and one frame per character:

| Offset | Type | Content |
|---|---|---|
| +0 | 2 × f32 | `27.0`, `654.0` |
| +8 | i32 | 0 |
| +12 | u32 | number of characters = Last − First + 1 |

## 6. Models (`.mdl16`, `.mdl`)

Implementation: `zaxtools/mdl.py`. All 1,119 `.mdl16` read: 2,660 sequences, 49,979 frames. [verified]

A binary serialised object tree. Objects start with `f32 27.0` + `f32 class signature`, strings are `u32 length` + characters. [verified]

1. **Model header = object `CModel`** [verified: all 1,119 models read completely, `zaxtools/modelhead.py`; since 2026-10-20 also the three items deployed by the player, Companion Drone, Autogun Medium and Proximity Mine].      - object = `f32 27.0`, `f32` class signature, `u32 n` + n × (name + pointer) "Dynamic Properties" (e.g. `Hue Remap`, before the fields in the text), then the fields of all base classes and of the class itself.
     - pointer = class name (`u32` length + text, empty = null) + object. Embedded objects (e.g. `BehaviorStack`, envelopes) have no class name; the class follows from the field. It comes from the text files (the same field there) or, where it is missing there, from the class's constructor that puts the sub-object at its offset: `CCompanionAI.Set Target Behavior` = `CEntityBehaviorStateSetClosestTarget` (+0xec, `0x46e2c2`), `CAutoGunAI.PickupAI` = `CPickupAI` (+0x30, `0x58ebc4` → `0x53d8f0`) [confirmed: Zax.exe; verified: both models read up to the path `Models/` with it]. 2. **Sequences**, signature `(27.0, 758.0)`:

       - Alpha/opacity blend, all 16-bit spans (`Blend16_AlphaPixel` `0x44bf70`), destination `d` and source `s` as RGB565, weight `w` 0…255: `a6 = w >> 2`, `a5 = a6 >> 1`, in 32-bit unsigned arithmetic
         `G = ((((s >> 5 & 63) − (d >> 5 & 63)) · a6 >> 1) + (d & 0xffe0)) & 0x7e0`,

         `B = ((s & 31) − (d & 31)) · a5 >> 5` (logical shift: a negative difference borrows from the green field, which the masks of G/R do not see),

A span (one RLE entry of the edge block, as the clipped row passes it) of n pixels blends its first `4 · ⌊n / 4⌋` pixels with the MMX blend and the last `n mod 4` with the scalar blend above. ## 8. Save games (`SaveGames/*.sav`)

[verified 2026-11-07 on 126 save games of the German 1308 build (the save game set of `zax-testtools` and the quick saves of test runs): every file follows the layout below, every embedded stream unpacks to its stated size; code: `App_LoadLayerStream` `0x59e3e0`, the save `0x5a0c80` (App slot 109), loading `0x4f3e70` (World slot 74), `Pack`/`Unpack` `0x5c3b40`/`0x5c3ba0`, `zax-decomp/docs/DECOMPILATION.md`]

A save game is the text format of section 2 in three parts; the first two stay unpacked so the load screen can list a save without unpacking it.

1. **`CZaxSaveGameStats`** (text) – what the load screen shows: `Save Date and Time` (text) and `SaveDateAndTimeNumeric` (Unix time), `Current Mission` (the mission with its objectives and the par statistics, empty outside a mission), `Screen Shot=CFrame(200,150,16)` (the preview, 16-bit pixels as hex lines – about 120,000 of the header's characters), `Player Health`, `Elapsed Time`, `Map Name`, `Ore In Inventory`, `Crystals In Inventory`, `SaveGame FileName`, `Item List` (the inventory lines as the screen shows them: category, label, quantity, colours), `Save Game Name`.
2. **`CSwappedLayerFilenameMappingTable`** (text with embedded binary) – the levels visited before, which the game keeps outside memory: `Layer Mapping Array` with one `CSwappedLayerFilenameMapping` per level (`Partial Layer Name`, `Current Temp File`, `Mission Temp File`, `Has Expired`, `Expired This Mission`), then `Mission Marker Temp File` and `LRU LayerSaveData Array`. A non-empty `TempFile` holds a line `Length=<n> bytes`, the line `#### BEGIN TEMPORARY FILE ####`, exactly `n` raw bytes and the line `#### END TEMPORARY FILE ####`. The raw bytes are a packed stream as in part 3: in the 126 saves 1,761 temporary files, 1,638 of them a `CLayerSaveData` (a level's state) and 123 a whole `CLayerHolder` (`Mission Marker Temp File`). [assumption, from the names and the expiry code ("Attempting to load expired map"): `Current Temp File` is a level's state when Zax left it, `Mission Temp File` its state at the start of the mission, the mission marker the world at the mission's start for a restart]
3. **The packed body**: three little-endian dwords – the mark `0x3e9` (1001), the packed size, the unpacked size – then one zlib stream (`compress2` level −1) of exactly the packed size, which ends the file. A stream without the mark is read unpacked (`0x59e3e0`). Unpacked, it holds five top-level objects:

| Object | Content |
|---|---|
| `CLayerHolder` | `Referenced Object List Location` (the offset of the line `Referenced Objects` in the unpacked text [verified: all 126]), `Object ID`, `UniqueID`, the playing times, `Current Active Layer`, and `Layer=CLayerSaveData`: the current level with every object in its current state – a level file (section 2.1) plus runtime state (`Has Begin Been Called`, `Shake Time`, …), the `Fog Of War` map (section 5, "Fog of war": what was uncovered stays uncovered) and the way point map |
| `CCharacterListHolder` | the players: references to their characters (`Player=0x… (CEntityWalking)`) |
| `CZaxSaveData` | `Mission Manager` (missions and their state), `Voice Log Array Data`, `NonInteractive Sequence`, `GameType Specific Data` (the statistics of the game type), `Difficulty` |
| `COtherMapList` | `ActionList`: actions waiting for other maps |
| `Referenced Objects` | the number of referenced objects and their `Object ID`s |

- **`Object ID`s are heap addresses** of the running game: every saved object carries its address as ID, and references between objects (`Player=0x029FA664 (CEntityWalking)`) use these IDs [confirmed: code; `zax-decomp/docs/DECOMPILATION.md`, "Batch 6-11"]. Two saves of the same game state from different runs therefore differ in their IDs unless the heap is laid out alike (the decompilation's comparisons renumber them, or fix the heap).
- Sizes in the 126 saves: 127,658 to 2,470,268 bytes; the body unpacks to 119,639 to 1,341,832 bytes.
