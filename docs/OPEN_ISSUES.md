# Open issues

Sorted by importance for the editor. Every item says how to clarify it.

## Clarified in the game (practical tests 2026-10-18, Windows VM)

Test level: `ACT 1/M1M2/01 Main`, file replaced in `DATA\Levels\ACT 1\M1M2\`, game without `Data.dat`.

1. **Does the game accept a changed `.zax`?** – **Yes** [verified]. The game runs completely from the unpacked folder `DATA/` if `Data.dat` is removed. If both exist, the file in `DATA/` wins [verified; cause confirmed, see FORMATS.md 1]. So `Data.dat` does not have to be removed.

2. **Does the game rebuild the `.way` itself?** – **Yes** [verified]. After deleting `01 Main.way` the game creates a new file when loading the level. The message "Calculating Way Point Map" was not visible. The AI behaves normally, and the opening scene runs through completely.
   Consequence for the editor: it does not have to compute way points. When saving a changed level it should leave out the matching `.way` from the output or mark it for deletion so the game rebuilds it. The generation procedure has been read in the exe (FORMATS.md 4) [confirmed 2026-10-20]. Comparison [verified 2026-10-20]: the `.way` the game regenerates for the unchanged `01 Main.zax` is identical byte for byte to the original (1,313,972 bytes, self loops included). The shipped `.way` files therefore come from the same procedure, and one rebuilt by the game is fully equivalent.
   Since 2026-10-29 the editor computes the `.way` itself exactly as the game (`zaxtools/waymap.py`, all 112 shipped files byte for byte, verified in the game with `Test/E2Cave`; FORMATS.md 4) and shows it (View → Way point network). Caveat found then: for an edited original level the deletion is not enough while the game has `Data.dat` – it loads the shipped `.way` from the archive (FORMATS.md 4); File → Write the way point map gives the game the new one.

3. **Does the mini map have to match?** – **No** [verified]. The game uses the outdated mini map from `Cache/Levels/…frm16` without errors; the ship appears there at the old position. Only a visual flaw.

4. **Objects that belong together (groups)** [verified]. If only `Spaceship` is moved (+300 px), the ship stands in the path of the enemies of the opening scene. One enemy then cannot be killed, and the mission hangs. If instead the whole group is moved by −200 px, everything works: enemies die, the dialogue runs, Zax gets into the ship. The group consists of `Spaceship`, `Ship door` (`CEntityAnimated`), `Zelon shooting` (invisible ship cannon: `CEntityWalking`, model Rogcoil, `Visible=0`, stands inside the ship), `Spawnpoint from ship`, the polygons `go inside` and `ship door poly` (`CFreeRangePoly`) and 7 smoke effects within 200 px.
   Which enemy failed in the first attempt, and why, is not exactly clear. It probably got stuck on the ship [assumption: needs a game test]. The only certainty: moving as a group works.
   Consequence for the editor: multiple selection and moving groups. Polygons move along. Show invisible helper objects (`Visible=0`) and editor objects. Show which objects are referenced from actions via `Name`.

5. **Adding and deleting objects** [verified, 2026-10-18]. A new object as a copy of an existing object with the same model (also from another level, name cleared, inserted at the end of the Tree List) works in the game: decoration appears, items can be picked up, a copied enemy (Rogcoil, `CEntityWalking`) moves and attacks. Removing a `Level Part` (the Tree List has no counter) loads without errors. The missing decoding of the templates in `.mdl` is therefore not needed for the editor for now.

6. **Minimal objects: missing fields get defaults – but apparently those of the class, not those of the model.** In the empty test level (`zax-testtools/tools/make_testlevel.py`), objects that only contain `Level Part=<class>`, `Name`, `Model`, `Position X/Y` and `Cur Sequence` work flawlessly: the tree group `Bent Trees 01` and the weapon pickup `PU Valeth Missile Launcher`. That is why the editor has created **all** new objects like this since 2026-10-18 (default object); copies from other levels and "donor" objects were dropped. Copying/duplicating existing objects in the editor, however, still copies everything.
   Second test (2026-10-18, test level with `--add`) [verified]: the torch `Torch 1` (`CEntityAnimated`) burns animated; the projectile `Orb` (`CEntityProjectile`) lies still. The enemies `Rogcoil`, `Crutch` (`CEntityWalking`) and `Skynuk` (`CEntityFlying`) do **not** attack and have **no collision**; `Sentinon` (`CEntityStationaryCharacter`) has collision but does not attack either. `Health Fruit 3` could not be checked (full health).
   Interpretation at the time [assumption, superseded by "Solved" below]: missing fields get the class defaults of the program, not the defaults from the model header. That is enough for decoration, effects and pickups; characters need `Collideable=1`, `Has Hit Points=1`, `Activity` (AI), `Inventory` (weapon) and possibly `Child List` (upper body) – in the original levels, e.g., 339 of 344 Crutches have exactly 1 AI entry and an inventory.
   **Solved** [verified 2026-10-18]: the model header (`CModel`) is decoded (FORMATS.md, section 6). Its "Default Entity" is the real default object; enemies created with it (`Rogcoil` with upper body, `Crutch`, `Skynuk`), the turret `Sentinon`, the projectile `Orb` and the torch work completely in the game. The editor has created new objects like this since then (needs Zax.exe); models without a default object stay minimal objects.
   Full test through the editor UI [verified 2026-10-18]: objects placed and duplicated in the empty test level via the model browser stand in the right place and behave as above (enemies with collision, attack and upper body, the turret shoots, the torch animates); a model used in no level (◇) also works.

A new level below `Levels/Test/` loads this way without further entries. ## Known limits of the renderer

- Rotation by the angle the game draws with (`LevelPart.draw_angle`, the movement angle; until 2026-10-29 `Start FacingAngle`, CLAUDE.md step 20): the editor always, the renderer only with `use_facing`/`--facing`, otherwise rotation 0; the frame is the one the game shows at level start (`zaxtools/anim.py`, step 30; until 2026-10-29 the first non-empty frame)
- Smoke and light: the renderer uses the exe's exact 16-bit integer arithmetic since 2026-10-28 [confirmed: code `0x44bf70`, `0x433df0`, `0x434280`; FORMATS.md 6, render mode; CLAUDE.md step 21]; the editor's map still blends in floating point (ColorDodge).
- Fog of war: only affects the mini map, not the game view; the renderer does not have to draw it (FORMATS.md, mini maps). A mini map from the editor does not show it. A full fog map also takes effect in single player [verified 2026-10-20, `Test/Nebel`; FORMATS.md 5.1].
- **Order of objects:** since 2026-10-18 renderer and editor sort by position Y + `Sorting Y` from the model header (`CModel`, in Zax.exe as "Debug/Sorting Y", integer at offset 0x44) [confirmed: code `0x488d70`/`0x4886a0`; verified 2026-10-18 and 2026-10-20]: for the torch (hot spot 30, image height 80, Sorting Y 47), palm (71/154/64) and Zax (25/50/19), position + Sorting Y lies exactly at the foot or the base of the trunk. Water banks (−400 … −605) and the ground marks `GroundSlashTest2/3` (−265/−173) slide down as a result; the stones and plants of the crash site in `01 Main` are no longer hidden (comparison image `out/vergleich_sorty_absturz.png`, not in the repository). Confirmed in the game: Zax disappears behind the palm trunk [verified 2026-10-18]. `jungle dirt 1–4` have large positive values (184–255); the clods of earth at the crash site in `01 Main` nevertheless lie below the ship's hull because their layer has `Render On Ground` (item 16) [verified 2026-10-20; the statement of 2026-10-18 that they lie above the edge of the hull was wrong]. `ScorchGround` has 0. Since 2026-10-20 every layer is also sorted in separately, with `Sorting Y Offset` and `Cutting Lines` per sequence (vertical strips with their own offset, item 15). Since 2026-10-20 also surfaces (`YSort`) and the ground queue for layers with `Render On Ground` (item 16). The "sorting offset" of the sequences read so far (always −100) is `Editor Display Offset` [confirmed: field order of the exe].
- `CFreeRangePoly` and `CWayPointsPolygon` are only drawn by the editor (as outlines, View menu: turquoise and green, can be shown and hidden individually), not by the renderer (`tools/render_level.py`)
